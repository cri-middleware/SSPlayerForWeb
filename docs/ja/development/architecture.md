# プレイヤーの構成

SpriteStudio Player for Web を開発する人と、自分のプロジェクトのために改造する人に向けたページです。部品をその役割で説明します。ビルド、変更した版をゲームやアプリで使う方法、実際のホストでの確かめ方は[ビルドガイド](/ja/development/build)にあります。各パッケージの README の末尾にあるコントリビューター向けの節が、そのパッケージに踏み込みます。

SpriteStudio の Player に共通すること（再生・モーションブレンド・サウンドキー・パーツトラッキングの振る舞い）は、SDK の[ポーティングガイド](https://github.com/cri-middleware/SpriteStudio-SDK/tree/develop/libs/ssruntime/docs)に一度だけ書いてあります。

## 層 {#layers}

ワークスペースは 2 つの側に分かれます。どのパッケージがどれの上に載っているかは、README の[構成図](https://github.com/cri-middleware/SSPlayerForWeb/blob/main/README.ja.md#monorepo-構成)にあります。

**再生側**は、ページやゲームの中で動きます。

- `ssplayer-core` はランタイムの WebAssembly 版を包み、各フレームを描画データに変えます。DOM にもエンジンにも依存しません。
- `ssplayer-webgl` はその描画データを素の WebGL で描き、ページに `<ss-player>` を提供します。`ssplayer-pixi` は PixiJS の表示オブジェクトとして描きます。`ssplayer-pixi-ui` は `ssplayer-pixi` のプレイヤーを `@pixi/ui` のボタンに入れます。`@pixi/ui` を連れてくるので、アニメーションを再生するだけのアプリが入れずに済むよう、別のパッケージにしています。
- ホスト向けのプラグインは `ssplayer-webgl` の上に載ります。`ssplayer-rmmz` は RPG ツクール MZ のプラグインです。アニメはピクチャに属するので、MZ が移動・拡大し、ゲームと一緒にセーブします。動かすのはプラグインコマンドです。`ssplayer-tyranoscript` は `[ss_*]` タグで、ティラノビルダーと TyranoStudio のランタイム側でもあります。各キャラクターは Tyrano のレイヤー上の `<div>` で、その状態はセーブに入ります。

**変換側**は、`.sspj` を `.ssab` に変えます。

- `ssconverter-core` はコンバーターの WebAssembly 版です。プロジェクトのバイト列を受け取り、`.ssab` のバイト列を返します。
- `ssconverter-web` は変換ページとその Node CLI です。
- `ssconverter-importer` は、エディタ用のプラグインが共有する自動インポートです。変更されたプロジェクトを見つけて変換し、変換ごとに書いたものを記録し、したことをログに残します。ティラノビルダーはプロジェクトを開いたとき、MZ はテストプレイの開始時に走らせます。ホストが渡すものは [README](https://github.com/cri-middleware/SSPlayerForWeb/blob/main/packages/ssconverter-importer/README.ja.md) にあります。
- `ssplayer-tyranobuilder` はティラノビルダーのエディタ側です。パレットのコンポーネント、プラグイン管理画面のパネル、ビルダーが走らせる形のインポーターから成ります。1 つのプラグインフォルダが、これを TyranoScript のランタイムと一緒に運びます。

## この作りになっている理由 {#why-it-is-built-the-way-it-is}

ここに挙げる理由はどれも複数のパッケージにまたがります。詳細は、関わるコードのコメントにあります。

**ホストごとのプラグインは、ホスト自身の GL コンテキストに描きます。** MZ のプラグインは MZ の PixiJS にレンダラーを登録し、生の描画の前後で、MZ 自身の Effekseer のスプライトと同じ状態の保存と復元を行います。そのためアニメは MZ のスプライトと一緒に並び、上に canvas は重なりません。TyranoScript のプラグインは Tyrano のレイヤーごとに canvas を 1 枚持ち、キャラクターの位置はその `<div>` から決めます。ブラウザが許す WebGL コンテキストは 8〜16 個ほどしかなく、`[anim]` と `[kanim]` が名前で見つけるのもその `<div>` だからです。

**MZ には SIMD を使わないランタイムを渡します。** MZ の NW.js は WebAssembly SIMD の無い Chromium で、既定のランタイムは SIMD を必要とします。コアは、スカラー版だと告げられない限り、そこで起動を拒みます。そのため MZ の ZIP と MZ のサンプルはスカラー版のランタイムを運び、Tyrano 系のプラグインは SIMD 版を運びます。

**変換はホストの開始時に行い、監視はしません。** `.sspj` を変換する 3 つのホストは、同じ時点を共有しています。開始時です。Ren'Py は開発者モードでゲームを起動したとき、ティラノビルダーはプロジェクトを開いたとき、MZ はテストプレイの開始時に変換します。MZ は F5 でテストプレイを再起動するので、SpriteStudio で保存して F5 を押すのが MZ での繰り返しのすべてです。その後、Ren'Py は自動リロード（Shift+R）を有効にすると保存を拾います。リロードがインポートをもう一度走らせるからです。ティラノビルダーには、プラグインが乗れる再読み込みの仕組みがありません。監視するならプラグイン自身がエディタのスレッドで行うことになり、ポーリングなら 1 回ごとにソースファイル 1 つにつき 1 回の `stat` がかかり、そのすべてがエディタを描画しているスレッド上の Electron の `contextBridge` 越しの同期呼び出しになります。しかも作者はその間 SpriteStudio を見ています。そこでビルダーは指示されたときに変換します。**今すぐ取り込む**（**プロジェクト → プラグイン** → **SpriteStudio**）はプロジェクトを開いたときと同じ変換を走らせ、**SpriteStudio 表示** コンポーネントの **今すぐ再変換** はそのアニメデータ 1 つを作り直します。

**ビルダーは、成功をトーストで、対処が要るものをダイアログで知らせます。** 再変換が終わるのは、作者が SpriteStudio で作業している最中であることが多く、モーダルにすると作業中のアプリからフォーカスを奪います。変換の失敗がダイアログなのは、理由そのものを見せる必要があり、エディタには頼れるコンソールが無いからです。名前の衝突がダイアログなのは、どちらかの名前を変えてもらう必要があるからです。一度も変換したことがなく `.sspj` も無いプロジェクトには、プロジェクトの置き場所を伝えるダイアログを出します。

**コンバーターは Worker で動きますが、読み書きするファイルは別です。** コンバーターの呼び出しは同期的で、エディタが固まるほど長くかかります。そのため Blob URL から起動した Worker で動かし、ホストが Worker を起動できなければ呼び出し元のスレッドで動かします。プラグインがファイルシステムに届く経路は `window.studio_api` だけで、それを持つのはエディタのスレッドだけなので、各プロジェクトの前後の読み書きはそこに残ります。これを移すことは、パッケージの [ROADMAP](https://github.com/cri-middleware/SSPlayerForWeb/blob/main/packages/ssplayer-tyranobuilder/ROADMAP.md) にあります。

**インポーターのフォルダは固定です。** MZ は `SpriteStudio_Source/` を読んで `spritestudio/` に書き、ティラノビルダーは `SpriteStudio_Source/` を読んで `data/others/ssdata/` に書きます。共有のインポーターはどちらの名前もオプションで受け取り、Ren'Py のインポーターはそれをゲーム側に公開していますが（`ss_source_dir`・`ss_output_dir`）、この 2 つのプラグインは公開していません。

**ビルダーが編集時に使うものは、書き出したゲームに入れません。** 書き出しは `index.html`・`data/`・`tyrano/` の 3 つを絞り込まずにコピーするもので、`.tbp` がファイルを届けられるのは `data/` の下にあるプラグインフォルダだけです。そのためプラグインは、そこにコンバーターの WebAssembly を見つけるとプロジェクトの `.ss_tools/` に移し、インポートの記録とログはプロジェクトのルートに置きます。

**1 つのプラグインフォルダに 2 つの半分を入れます。** `.tbp` はエディタ側と TyranoScript のランタイム（`init.ks`・`main.js`・`ssruntime_bg.wasm`）を 1 つの `ssplayer/` フォルダに入れて運びます。ランタイムが無いと、コンポーネントで組んだシナリオはエディタでは問題なく読めても、ゲームでは未知の `[ss_init]` で失敗します。1 つのプラグインにすることで、ビルダーのプラグイン数の上限も 1 つ分で済みます。作者が `.tbp` と TyranoScript の ZIP の**どちらか一方**だけを入れ、両方は入れないのはこのためです。どちらも同じ `data/others/plugin/ssplayer/` に展開されるので、重ねるとエディタ側とランタイム側の版がずれます。

**ホストごとのインポーターの報告先。** ティラノビルダーのメインウィンドウには DevTools が無いので、インポーターは `<project>/ss_import_log.txt` に、その都度、セッションをまたいで書きます。MZ のテストプレイにはコンソール（F8）があり、エラー画面がプロジェクト名と理由を表示するので、MZ はログファイルを書きません。
