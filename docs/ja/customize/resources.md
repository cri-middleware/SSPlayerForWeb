# リソースとライフサイクル

複数のプレイヤーで何が共有され、何がプレイヤーごとに確保され、`destroy()` が実際に何を解放
するかをまとめます。1 ページに多数のプレイヤーを置く前や、破棄まわりでリークや表示消えが
起きたときに参照してください。

## 共有されるもの・プレイヤーごとのもの

| 対象 | スコープ | 補足 |
|---|---|---|
| WASM モジュールとメモリ | **ページに 1 つ** | `initialize()` はモジュールレベルのシングルトンなので、複数回呼んでも問題ありません。 |
| テクスチャ（PixiJS） | **すべての `SSPlayer` で共有** | セルマップハッシュをキーに Pixi のグローバル `Assets` キャッシュへ登録されるため、同じアトラスを使う 2 つのプレイヤーは 1 つの GPU テクスチャを再利用します。 |
| テクスチャ（WebGL） | **プレイヤーごと** | `WebGLTexture` は生成したコンテキストに属し、`SSCanvasPlayer` はそれぞれ自前の canvas とコンテキストを持ちます。そのため同じアトラスでもプレイヤーの数だけアップロードされます。 |
| 埋め込みテクスチャ（`--embedded`） | **プレイヤーごと** | `.ssab` 自身のバイト列からデコードされ、意図的に共有キャッシュの外に置かれます。`destroy()` で解放されます。 |
| パース済み `.ssab`（WASM） | **プレイヤーごと** | `load()` のたびに `SSABResource` が作られます。HTTP フェッチはブラウザキャッシュに当たり得ますが、パース済みの WASM 側のコピーはプレイヤー間で共有されません。 |
| インスタンスパック | **プレイヤーのツリー単位** | インスタンスパーツが参照するパックはパックハッシュで重複排除され、そのプレイヤーのインスタンス子と共有されます。 |

実務上の帰結として、**同じキャラクターを N 体出すとパース済み `.ssab` も N 個**になります。
WebGL ではさらにテクスチャのアップロードも N 回発生します。

## 同じアニメを大量に出す場合

`ssplayer-pixi` を選んでください。描画をバッチ化し、テクスチャも `Assets` キャッシュ経由で
共有するため、単一コンテキスト上で多数のキャラクターを少ないドローコールに収められます。

`ssplayer-webgl` は、独立したプレイヤーを少数置く用途に向いています。`SSCanvasPlayer`（および
`<ss-player>` 要素）はそれぞれ自前の WebGL コンテキストを作りますが、ブラウザは同時に生存
できるコンテキスト数を制限しており、その上限はブラウザによっておおむね 8〜16 程度です。上限を
超えると古いコンテキストから破棄され、canvas が真っ白になる形で表面化します。数十体を同時に
画面へ出すなら、要素を数十個並べるのではなく PixiJS のシーン 1 つにまとめてください。

## 破棄する

`destroy()` は必ず呼んでください。冪等なので、フレームワークの後始末から念のため 2 回呼ばれても
安全です。

```ts
player.destroy();
```

解放されるのは、そのプレイヤーの WASM アロケーション（ランタイムコンテキスト、`.ssab`
リソース、インスタンス／エフェクトの子スロット）、レンダラーの GPU オブジェクト、および
そのプレイヤーが所有するテクスチャです。

::: warning PixiJS: 共有テクスチャは意図的に解放しません
`destroy()` は URL から読み込んだテクスチャを **`Assets.unload()` しません**。ほかの `SSPlayer`
がまだそのテクスチャで描画している可能性があり、取り上げるとそちらの表示が消えるためです。
解放されるのは、そのプレイヤーが単独で所有する埋め込み（`--embedded`）テクスチャだけです。

グローバル `Assets` キャッシュの管理はホスト側の責務です。ほかの Pixi アセットと同じように、
シーンを使い終わったタイミングで自分でアンロードしてください。
:::

WASM ハンドルには最後の保険として `FinalizationRegistry` が仕掛けてありますが、GC のタイミングは
規定されておらず、ファイナライザーが走らないこともあります。リーク対策の保険であって破棄手順
ではないと考え、`destroy()` を呼んでください。

## WebGL のコンテキストロスト

`SSCanvasPlayer` が面倒を見ます。`webglcontextlost` / `webglcontextrestored` を監視し、
コンテキストが失われている間は描画を止め、復帰時には GL オブジェクトを作り直してすべての
テクスチャを再アップロードしてから再開します。テクスチャが欠けたままのフレームは描画されません。
これはコンテキストを積極的に破棄するモバイル webview で特に効きます。この処理がなければ
canvas は復帰せず白いままになります。

テクスチャは保持しておいた生成情報から復元されます。URL は再フェッチ、埋め込みバイト列は
再デコードです。ひとつだけ利用側の協力が要るのが、`bindTextureSource()` で自分で渡した
テクスチャです。元の `TexImageSource` からそのまま再アップロードするため、そのソースを手放して
いると（クローズ済みの `ImageBitmap` など）その項目は警告付きでスキップされ、描画されません。

## テクスチャを自分で供給する

テクスチャは通常 `.ssab` の兄弟ファイルとして解決されます。それ以外の場所から供給したい場合
（インメモリのバンドル、エンジンが既に GPU 上に持っているアトラスなど）は、
[`IResourceManager`](/api/@spritestudio/ssplayer-core/interfaces/IResourceManager.md) を実装して
コアを直接駆動するか、WebGL であれば `setAnimation()` の前に `bindTextureSource()` で
セルマップハッシュに紐づけて登録してください。

URL で辿れないインスタンスパックも同様で、
[`InstancePackProvider`](/api/@spritestudio/ssplayer-core/type-aliases/InstancePackProvider.md)
でバイト列を渡します。この場合コアはフェッチを行わなくなるため、そのパックのテクスチャ登録も
利用側の責務になります。
