# パフォーマンスチューニング

効果の大きい順に並べています。コマ落ちしているなら、まず解像度から手を付けてください。
エフェクトの多いコンテンツでは、このページのほかのどの項目よりも支配的です。

## 解像度とオーバードロー

SpriteStudio のコンテンツはたいてい CPU ではなく **フィルレート律速**です。エフェクトや
パーティクルのパーツは、大きくてほとんど透明な矩形を何枚も重ねるため、同じピクセルが何度も
シェーディングされます（*オーバードロー*）。コストは描画バッファのピクセル数 × 各ピクセルを
覆う層の数に比例するので、**描画バッファの解像度が最大のレバー**になります。3× のデバイスで
バッファを 2× に抑えれば処理は半分以下に、1× なら 9 割近く減ります。

**WebGL** — デバイスピクセル比に上限をかけます。既定でも `2` が上限です。

```ts
const player = new SSCanvasPlayer(canvas, { maxDPR: 1.5 });
player.resize(cssWidth, cssHeight);       // 上限を反映してバッファを再計算します
```

```html
<ss-player src="/assets/Ringo.ssab" animation="run" max-dpr="1.5"></ss-player>
```

**PixiJS** — 描画バッファは `Application` のものなので、そちらで上限をかけます。

```ts
await app.init({ resolution: Math.min(window.devicePixelRatio, 1.5), autoDensity: true });
```

同じタイミングで `antialias` を切ってみる価値もあります。描画対象はテクスチャ付きの矩形なので、
MSAA の効果は小さい一方で帯域を消費します。

::: tip 本当にフィルレート律速か確かめる
canvas を面積で 1/4 に縮めて、フレーム時間がおおむね比例して下がるか見てください。下がるなら
解像度がレバーです。ほとんど変わらないなら原因は別のところにあるので、ドローコール数と下記の
再生オプションを確認してください。
:::

## そもそも描画しない

`ssplayer-webgl` の `pauseWhenHidden` は **既定でオン**です。`IntersectionObserver` で canvas が
画面外にスクロールしたときにティッカーを止め、`visibilitychange` でタブがバックグラウンドに
回ったときにも止めます。見えていない間も再生を進めたいという要件がなければ、オンのままに
してください。切る場合は `pause-when-hidden="false"` で明示的に指定します。

## 再生オプション

```ts
player.subframe = false;  // サブフレーム補間を無効化（既定は on）。負荷を抑えたいとき
```

- **`subframe`**: **既定でオン**。高リフレッシュレートやスロー演出で滑らかになります。
  多数同時再生で計算コストが重い場合は `false` に。
- **`frameSkipEnabled`**: **既定でオン**。描画が間に合わないときはフレームをスキップして
  再生タイミングを維持します。パフォーマンス目的での設定は不要です。

::: warning
`subframe` と `frameSkipEnabled` はセットで動作します。片方を off にする場合はもう片方も
off にしてください。片方だけ無効にすると再生タイミングが崩れます。
:::

## バッチが分割される要因

どちらのレンダラーも 1 フレームを少数のバッチで描きます。次の 2 つはそのバッチを分割し、
コストは関係するパーツ数に比例します。

- **統合シェーダー（`ss-*`）**。シェーダーパーツを含むバッチは、正しく合成されるように
  **パーツ単位**で、それぞれ専用のプログラムとユニフォームを使って描画されます。シェーダー
  パーツのないフレームはこの判定自体をスキップするので、コストはかかりません。
  [シェーダーとブレンドモード](/ja/customize/shaders)を参照。
- **マスク**。マスク対象のコンテンツは、専用のカバレッジ事前パスを通ります。マスクパーツを
  使わないアニメーションでは `player.maskEnabled = false` でこのパスを省けます。

どちらも避けるべき機能というわけではありません。同程度のパーツ数なのに片方だけ極端に重い、
というときに最初に確認する箇所です。

## 設計上の高速化

以下は何もしなくても効いています。

- **Direct Drawing（バッチ描画）**: 描画をバッチ化し、多数のキャラクターを少ないドローコールで
  描きます。
- **Zero-Copy**: トランスフォームやジオメトリは WASM メモリを直接参照する
  `Float32Array` ビューで受け渡し、毎フレームのコピーを避けます。
- **テクスチャ共有（PixiJS）**: アトラスはセルマップハッシュをキーに Pixi のグローバル
  `Assets` キャッシュへ入るため、同じキャラクターを多数出しても GPU テクスチャは 1 つです。

一方、**パース済みの `.ssab` は共有されません**。`load()` のたびに WASM 側のコピーが確保され、
WebGL ではプレイヤーごとに GL コンテキストが別なのでテクスチャも個別にアップロードされます。
同じキャラクターを大量に出すなら、多数のプレイヤーを並べるより PixiJS のシーン 1 つにまとめる
ほうがはるかに安上がりです。[リソースとライフサイクル](/ja/customize/resources)を参照して
ください。
